# Release 0.2.0 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Prepare synchronized Cargo and npm `0.2.0` metadata, release notes, and dry-run verification for the next Portzilla release.

**Architecture:** Keep release preparation declarative and credential-free. Version manifests and changelog describe the already implemented behavior; `docs/RELEASING.md` documents manual publication/tagging steps. No tag, push, registry publish, or workflow automation is performed by this change.

**Tech Stack:** Cargo package metadata, npm package metadata, Markdown, Cargo publish/package tooling, npm pack.

---

### Task 1: Bump synchronized package versions and add release notes

**Files:**
- Modify: `Cargo.toml`
- Modify: `Cargo.lock`
- Modify: `package.json`
- Create: `CHANGELOG.md`

**Step 1: Update both manifests**

Set the package version to `0.2.0` in `Cargo.toml` and `package.json`. Regenerate the root package entry in `Cargo.lock` through Cargo rather than editing dependency versions manually.

**Step 2: Add the `0.2.0` changelog entry**

Describe the user-visible changes: lease identity/PID-reuse hardening, versioned state format v2 and upgrade warning, OS occupancy-aware reassignment, multiplatform CI, optional foreground `watch`, and shared hook-adapter evaluation. Include compatibility and known limitations without claiming that the tool manages or kills processes.

**Step 3: Verify manifest synchronization**

Run:

```bash
test "$(sed -n 's/^version = "\(.*\)"/\1/p' Cargo.toml)" = "$(node -p "require('./package.json').version")"
```

Expected: both versions are `0.2.0` and Cargo metadata succeeds.

### Task 2: Update the release procedure

**Files:**
- Modify: `docs/RELEASING.md`

**Step 1: Update release examples**

Replace the old `v0.1.0` tag example with `v0.2.0`. Clarify that the release tag must match both manifest versions.

**Step 2: Add release-readiness checks**

Document commands for formatting, Clippy, complete tests, `cargo publish --dry-run`, `npm pack --dry-run`, and explicit version comparison. Keep publication, tagging, and pushing manual and ordered after validation.

**Step 3: Document package-content checks**

State that the Cargo and npm dry-runs should be inspected for expected files only and must not include `target/`, local state, credentials, or plan artifacts.

### Task 3: Verify release artifacts and final scope

**Files:**
- Test: `Cargo.toml`
- Test: `Cargo.lock`
- Test: `package.json`
- Test: `CHANGELOG.md`
- Test: `docs/RELEASING.md`

**Step 1: Run code quality checks**

Run:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets --all-features
git diff --check
```

Expected: all commands pass.

**Step 2: Run package dry-runs**

Run:

```bash
cargo publish --dry-run
npm pack --dry-run
```

Expected: both commands succeed or report only environment-specific registry warnings; inspect file lists and confirm no build artifacts, state files, credentials, or untracked planning artifacts are packaged.

**Step 3: Search stale version references**

Run:

```bash
rg 'v?0\.1\.0' Cargo.toml Cargo.lock package.json README.md docs CHANGELOG.md
```

Expected: no stale release-target references remain, except historical context explicitly identified as such.

**Step 4: Review final status**

Run:

```bash
git status --short
```

Confirm release-preparation files are intentional and do not include generated package archives. Do not push or publish until the release candidate is reviewed.
